## 2 最关键的发现：瓶颈不在守卫

报告 §3.3 的 25 对切片就是 **slack 的 user_task_0–4 × injection_task_1–5**，
和我们跑的是同一批。把三方放在一起：

| 同一 25 对（slack） | ASR | UA |
|---|---:|---:|
| 报告 · IPIGuard | 20.00% | 0.80 |
| 报告 · EAG-Guard | 4.00% | 0.92 |
| 本仓库 · 无防御 | 44.00% | **0.28** |
| 本仓库 · EAG-Guard | **0.00%** | **0.20** |

**我们的无防御臂只有 0.28，而报告带守卫是 0.92。** 这不是守卫的差距，是
**智能体脚手架**的差距：我们用极简 ReAct（一句 system prompt + 3 轮），
AgentDojo 官方 pipeline 有完整 system prompt 和更多轮次。模型没被拦也做不完题，
再谈"守卫吃掉了多少效用"就没有意义。

> 结论：先把脚手架对齐，否则后面每一组数都不可比。

## 4 路线图

### P0 脚手架对齐（1–2 轮，最高优先）

- 换成 AgentDojo 官方 system prompt（`PipelineConfig` 的那份），而不是我们自己写的一句话
- ReAct 轮次 3 → 6–8
- 用 workspace + slack 各 25 对重测两臂，目标是 **无防御 UA 达到报告量级**（slack ≈ 0.72）

**判据**：无防御 UA 与报告差距 < 0.10，才继续往下走。

### P1 四域 25 对 + 干净基线（2–3 轮）

- travel / banking 接入，四域各跑 25 对两臂 + 干净基线
- 补两个已知缺口：`participants` 跨来源委托（contacts + inbox）、`new_end_time` 裁判豁免验证
- 产出第一张四域对照表

### P2 全量 629 对（3–5 轮）

- 每域 240/105/140/144 对，两臂
- 成本：25 对约 5 分钟，四域两臂约 1.5–2 小时；缓存命中后重跑接近免费
- 与 `results/baseline_report.json` 对表，逐域记录差异

### P3 消融复现（1–2 轮）

按表 4-2 逐项：只读策略（banking/slack）、语义 vs 结构（25 对）、严格度（249 对）、
输出审核（travel）、反馈强弱（banking）。

### P4 归档（1 轮）

复现手册 + 四域结果表 + **差异说明**（哪些数字对不上、为什么、是否环境差异）。

## 5 风险与判断

1. **报告数字可能来自更强的脚手架**。若 P0 对齐后 UA 仍差 0.2 以上，说明还有实现差异，
   要按 §4.3 的消融逐项反推，而不是继续调守卫。
2. **工具级 ASR 目前是启发式**（看注入目标里的对象标识有没有出现在执行参数里）。
   跑满一域后应换成环境状态差，否则 0/609 这种数不可信。
3. **单对成本不低**（每对 2–6 次模型调用）。全量实验前先确认预算，或用缓存分批。
4. **provider 非确定性**：temperature=0 也会漂，同一配置两次跑可能差 1–2 对。
   对比必须同批、同缓存状态（或都关缓存）。
