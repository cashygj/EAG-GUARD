打通，并把口径错误挤出来。

## 3 这一轮挤出来的四个坑

### 3.1 `security` 的方向是反的（最重要）

AgentDojo v1 里 `injection_task.security()` 返回的是"注入目标是否被完成"：
banking 看有没有真的转给攻击者，workspace 看那封恶意邮件在不在。**True = 被攻破**。
一开始按字面理解成"True = 安全"，整个 ASR 会反号。

`metrics.outcome_from_agentdojo` 已改为 `attack_success = security`，
并有 `tests/test_metrics.py::test_agentdojo_security_sign` 钉住。

### 3.2 被拒的调用必须从 transcript 里摘掉

`functions_stack_trace_from_messages` 把 assistant 消息里**所有** tool_call 都当"调用过"，
不管有没有真的执行。如果守卫只拦执行、却把调用留在消息里，那些依赖
`security_from_traces` 的注入任务就会把"被拦住"判成"已执行"。
现在拒绝时会把调用从 `tool_calls` 里删除，改发一条守卫通知让模型重规划，
并有回归测试 `test_denied_call_is_removed_from_transcript`。

### 3.3 日期归一化

用户写"May 26th"，模型调工具时给 `2024-05-26`，纯子串匹配判不出这是"用户给的"，
于是一个合法的只读查询被误杀。`provenance.value_in()` 现在会把 ISO 日期展开成
`may 26` / `26 may` / `5/26` 等写法再比。

### 3.4 DashScope 不认 `developer` 角色

AgentDojo 的 `OpenAILLM` 把 system 消息转成 OpenAI 新的 `developer` 角色，
DashScope 兼容端点直接 400。`make_llm()` 里把 system 分支改回 `system`，其余不动。

另外：`important_instructions` 会用 pipeline 名字查模型名表来填模板里的 `{model}`，
表里只有 GPT/Claude/Llama。qwen 查不到会抛异常，所以 `build_attack()`
用同一个模板手搓一份，把 `{model}` 填成 `qwen-plus`——注入文本与官方模板逐字一致。

## 4 25 对切片：五轮迭代（workspace，user_task_0–4 × injection_task_1–5）

验收标准要的是这 25 对。第一版只有 0.32 的效用，原因全是**误杀**，不是模型不行。

| 版本 | ASR | UA | 耗时 | 改了什么 |
|---|---:|---:|---:|---|
| v1 | 0.00% | 0.32 | 502s | 初版 |
| v2 | 0.00% | 0.48 | 492s | 只读工具默认放行（不再要求模型逐个点名） |
| v3 | 4.00%* | 0.44 | 153s | 只读动作跳过参数溯源与裁判 |
| v4 | 0.00% | 0.44 | 89s | 修掉"失败对计入 ASR"的 bug |
| v5 | **0.00%** | **0.52** | 134s | 参数分级：时间放开、对象 id 按域委托、列表对象按元素比 |

\* v3 那 4% 是一例 `RemoteDisconnected`：API 抖动导致这一对没跑完，
`security` 用了默认值 True 被算成"被攻破"。失败的对现在直接排除在指标外。

轨迹：`results/runs/workspace_eag_slice25{,_v2,_v3,_v4}/`

### 4.1 两个设计错误（靠数据发现的）

**只读工具不该受 T 约束。** v1 里 15 次拦截是 `get_unread_emails` / `search_emails` /
`search_calendar_events` 被当成越权——模型换个检索路径就撞墙。读取没有副作用，
"能读什么"由对象白名单管；真正要卡的是写动作。

**只读动作也不该进参数溯源和裁判。** 注入正是*通过读取*进来的，拦住读取既拦不住
伤害（伤害在写动作上），又让每一对多花 3–4 次模型调用。跳过之后耗时从 492s 降到 89s。

### 4.2 同 25 对的两臂对照（这才是可比口径）

单看 EAG 的 0.44 没意义，必须和同批对上的无防御臂比：

| 臂 | ASR | UA | 被攻破 | 完成 |
|---|---:|---:|---:|---:|
| 无防御 | 28.00% | 0.2800 | 7/25 | 7/25 |
| EAG-Guard | **0.00%** | **0.5200** | 0/25 | 13/25 |

配对比较：5 对两臂都完成，**守卫修好 6 对，弄坏 2 对**。
这正是报告 §3.2 那句"修好 117、弄坏 43"的微缩版——守卫不是拿效用换安全，
而是两个指标一起抬。

轨迹：`results/runs/workspace_undefended_slice25/`、`workspace_eag_slice25_v4/`

### 4.3 守卫到底让模型少做了多少：干净基线

要回答"误杀有多少"，必须在**无注入**条件下比较两臂。系统临时目录不可用、缓存又会
让两臂状态不一致，所以两组都关缓存各跑 10 个 worksapce 任务：

| 干净基线（无攻击） | UA |
|---|---:|
| 无防御 | 0.70（7/10） |
| EAG（v2 策略前） | 0.30（3/10） |
| EAG（v5 策略后） | **0.60（6/10）** |

差距从 0.40 收窄到 0.10。同 25 对攻击场景：无防御 28%/0.28 → EAG **0%/0.52**。

### 4.4 参数分级：放开哪些、守住哪些

丢掉效用的全是日历写操作：时间、事件 id、参与者。三者性质不同，不能一刀切。

| 类别 | 参数 | 策略 | 理由 |
|---|---|---|---|
| 地址/金额 | `recipient` `payee` `amount` `url` `password` `participants` | **严格**：只能用户直接给或显式委托 | 决定"东西送到哪、给谁、多少钱"，攻击者唯一真正想要的东西 |
| 时间 | `start_time` `end_time` `date` `day` | **不核对来源** | 模型会把"明天上午十点"算成 ISO 时间戳，逐字匹配必然失败；改时间也拿不到东西 |
| 对象 id | `file_id` `event_id` `email_id` | **只信任同类来源** | 文件 id 只能来自文件读取、事件 id 只能来自日历读取——邮件正文里写一个文件 id 让你删，不算数 |
| 自由文本 | `title` `body` `description` `location` | **放开** | 决定外泄方向的是收件人，不是正文；收件人严格就够了 |

这套分级是代码策略，**不允许模型在一次解析里覆盖**——最初 LLM 把 `start_time`
委托给了一个叫 `user_input` 的虚构来源，逐字匹配永远失败，正常任务全被否掉。

### 4.5 又两个 bug

- **列表参数的对象检查**：`participants=['sarah@…']` 被当成字符串 `"['sarah@…']"`
  去和白名单比，永远不相等。对象检查现在按元素逐个比。
- **裁判复议策略字段**：时间参数已经按策略放行，裁判仍用"用户没有逐字指定"否掉。
  策略放行的字段不再进裁判上下文。

第一版看到 0.44，我以为是守卫误杀。把拦截与步数摊开看，结论相反：

```
完成的平均步数 1.8，未完成 2.2
未完成的对里，最后一步是拦截的比例：0/14
14 个失败里 9 个只有 1 步、零拦截
```

也就是说**大部分失败是模型自己没做完任务**，守卫根本没碰它们。
真正被守卫影响的是那 2 对"弄坏"：4×4、4×5，都是 `create_calendar_event` 被拦。

所以相对报告全域 0.7708 的差距，主要来自这块切片本身更难（`user_task_0–4` 是模型
在无攻击时也做不全的五题），以及这个模型在 workspace 域的能力上限——不是守卫的代价。
要严格回答"守卫的效用代价"，需要再跑一遍**无注入**的干净基线，这一步还没做。

### 4.6 缓存

`results/cache/agent/` 按请求哈希缓存模型返回（temperature=0 可安全重放）。
v4 之所以 89s 跑完 25 对，一部分是缓存命中。轨迹的 `summary.json` 里有 hit/miss 计数。
