# banking 的结构性改造：证据切片 + 字段级溯源

## 1 问题

banking 的守卫代价一直很高，且有一个绕不过去的判断：

> 收款人的合法值（账单里的 IBAN）和攻击者要的值（注入正文里的 IBAN）
> 都出现在**同一批工具返回**里，靠字符串匹配无法区分。

实测造成的后果：攻击成功（放行注入 IBAN）与误杀（拦掉合法 IBAN）同时存在。

## 2 报告怎么规定的

- §2.3：**工具返回被切分为带来源标签的证据**；
- §2.2：判定用**字段级溯源可达性（FPR）**——从参数节点沿 supports/derives
  回溯到直接授权或委托节点。

我们从没实现"切片"，也没有从工具返回里抽结构化字段，所以只能退回字符串匹配。

## 3 实现

`integrations/slicing.py`：把一次工具返回切成一记录一条证据，并抽字段。

| 工具 | 切片 | 抽出的字段 |
|---|---|---|
| `get_most_recent_transactions` / `get_scheduled_transactions` | 每笔交易一条 | recipient / sender / amount / date / subject |
| `read_file`（含 IBAN 与 Total 的账单） | 整份一条 | amount（Total）/ recipient（IBAN） |

字段级委托**只在字段里找值**。攻击者把 IBAN 写进交易记录的 `subject` 正文，
那只是文本，不构成任何字段，因此冒充不了收款人。

### 单元验证

```
付款给 UK12345678901234567890  → recipient: user_delegated ✓
付款给 US133000000121212121212 → recipient: injected       ✓
```

## 4 效果（banking 全域 144 对）

| 配置 | ASR | UA |
|---|---:|---:|
| 切片前 | 2.08% | 0.5417 |
| **切片后** | **0.69%** | **0.5417** |

**安全指标降了三分之二，效用一分没掉。** 这是本项目唯一一次"纯赚"的结构性改动。

## 5 试过但净负、已回退

**字段别名**（收款人也可来自交易的 `sender` 字段，为支持"退钱给给我转账的人"）：

| | ASR | UA |
|---|---:|---:|
| 切片 | 0.69% | 0.5417 |
| 切片 + 字段别名 | **2.78%** | 0.5417 |

注入交易里的 `sender` 同样能被冒充，净负。保持只认 `recipient`。

## 6 当前水位

| banking 144 对 | ASR | UA |
|---|---:|---:|
| 报告 | 0.00% | 0.7153 |
| 本实现 | **0.69%** | 0.5417 |

安全侧已经贴住报告（0.69% vs 0.00%）；剩下的 0.17 全在效用，
而它来自"无防御时智能体把任务做完的比例"（0.5972 vs 报告 0.7569）。
