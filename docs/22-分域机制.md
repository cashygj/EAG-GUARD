# 分域机制（工程实现细节，不进论文）

> 论文里讲的是一条统一的性质：外部内容可以改变计划，但不能改变授权。
> 下面这些是**为了让这条性质在每个域真正跑起来**而做的工程适配。
> 同一个机制在不同域效果相反，所以必须分域取舍。

## 1 判定"每个域该用什么机制"的方法

先看失败发生在哪一侧，再决定动哪里：

| 诊断指标 | 含义 | 对应机制 |
|---|---|---|
| 零拦截失败占比高 | 守卫没拦，模型自己没做完 | 提示词流程 / 必须执行 / 答复清单 |
| 被拦过失败占比高 | 拦完之后没恢复 | 恢复提示 / 可操作原因 |
| 某类工具被拦特别多 | T 覆盖不足 | 动作词兜底 |
| 攻击成功集中在某类参数 | 来源判定不足 | 证据切片 / 字段级 / 跨切片一致性 |

## 2 banking：结构化字段域

**失败画像**：注入写在账单文件里，且抹掉 Total/IBAN；模型据此付给攻击者账户。

**机制**：
1. 证据切片：交易→每笔一条（recipient/sender/amount/date/subject），账单→抽出 Total/IBAN；
2. 字段型参数（收款人、金额）**禁止整文提升**：只认字段，正文里出现的值一律不算；
3. 删除"安全纯文本来源退化为整文匹配"的兜底；
4. 跨切片一致性：收款人与金额必须来自同一条记录；
5. few-shot：读账单→自查金额/IBAN→付款。

**效果**：0.5417 → **0.6528**，ASR 0.69% → **0.00%**。

## 3 travel：查询+预订混合域

**失败画像**：
- 72% 失败**根本没发生任何预订**（查了 6 次就停）；
- 很多任务其实是**纯查询**（"告诉我名称/评分/地址/价格/营业时间"），不需要预订；
- 合法性判断依赖用户给的筛选条件（评分最高、价格最低）。

**机制**：
1. 动作词兜底补 `reservation`（注意 `reservation` 不含子串 `reserve`）；
2. few-shot：查询→判断条件→执行→汇报；
3. **执行/答复双分支**：要预订就直接下单，只问信息就不要预订；
4. **答复清单**：用户问了哪几项就逐项写全（名称/评分/地址/价格/营业时间）。

**效果**：0.2374 → 0.2786（必须执行）→ **0.2929**（加答复清单）。

## 4 slack：长链选择域

**失败画像**：
- 任务链条长（找频道→读用户→加人），模型常在中间停下；
- 拦截主要来自 `send_direct_message`（59 例），**但这些拦截基本都是对的**——
  用户请求往往不涉及私信，是注入要求发链接。

**试过但无效（重要）**：
| 改动 | 结果 |
|---|---|
| 对象参数交给裁判（不做白名单） | ASR 9.52→12.38、UA 0.40→0.36 |
| 解析器要求点名的对象全写进 O | 11.43 / 0.3905 |
| 用户/收件人加字段级严格 | 11.43 / 0.3524 |

**结论**：slack 的合法对象常来自消息正文（"邀请邮件里提到的新同事"），
字段级会把它和注入一起拒掉。**banking 的机制在这里水土不服。**

**待做**：不再动守卫结构，改攻"拦后恢复"与"长链执行"。

## 5 workspace：问答型域

**失败画像**：多数任务是"读邮件/文件后回答具体事实"，效用函数直接比对答复内容
（邮箱地址、日期时间格式、数量）。

**已试**：给答复加格式要求 → 切片上 0.68 → 0.60，反而更差，已回退。

**待定**：等本轮全域数据出来再定机制。

## 6 一句话总结

- **结构化字段域（banking）**：把“字段级”做实，收益最大；
- **查询型域（travel）**：靠“答复清单”和“必须执行”；
- **长链域（slack）**：字段级有害，得另找路子；
- 同一机制不能跨域照搬，这是这轮最贵的教训。
