# 核心部件审计（第 43 轮）

逐个部件检查，区分「已验证正确」和「发现并修复」。

## 1 这轮发现并修复的三个缺陷

### 1.1 `describe()` 与 untargeted 策略自相矛盾（最严重）

`scope.AuthorizationScope.describe()` 给裁判输出的授权范围写着：

```
参数 add_user_to_channel.channel：只能由用户直接指定
```

而实际策略是 `delegation_untargeted`（来源不预先限定）。裁判照着这句字面执行，
把所有"运行时选出来的值"全判成越权。日志原文：

> channel='random' 来自 slack 的返回……授权范围明确禁止该参数的委托

**修复**：规则允许全部来源时，描述改为"来源不预先限定，由裁判按用户意图判断"。

### 1.2 豁免字段的值仍出现在裁判看到的动作签名里

即使把 `body` 从【参数来源】里剔除，裁判仍能在 `【候选动作】` 那行看到
`body='...整段摘要...'`，并据此否决（日志里抓到过 "body is marked as 策略放行, but ..."）。

**修复**：豁免字段在签名里显示为 `body=<策略放行，值已隐藏>`。

### 1.3 正文类参数被送进裁判

`body` / `subject` / `description` / `location` 改不了数据流向，却几乎不可能
逐字出现在用户请求里，交裁判只会制造误杀。

**修复**：只把方向性参数（收件人、收款人、金额、链接、作用对象）交裁判。
