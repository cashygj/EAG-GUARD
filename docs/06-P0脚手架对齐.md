# P0：脚手架对齐（2026-10-25）

路线图里判断"数值不可比的根因是智能体脚手架"，这一轮做验证。

## 1 换了什么

| 项 | 之前 | 现在 | 依据 |
|---|---|---|---|
| system prompt | 我们自己写的一句话 | AgentDojo 官方默认模板 | 官方模板点名用户身份、要求用工具消歧、不许假设年份 |
| ReAct 轮次 | 3 | 6 | 之前模型常在答完前就用光轮次 |
| 失败对处理 | 计入 ASR | 排除并单独计数 | 一次 API 抖动会被算成"被攻破" |

## 2 效果（slack 25 对，同批）

| 指标 | 旧脚手架 | 新脚手架 |
|---|---:|---:|
| 无防御 ASR | 44.00% | 60.00% |
| 无防御 UA | 0.2800 | **0.4000** |
| 干净基线 UA（5 个任务） | — | **0.8000** |

干净基线 0.80 说明**模型本来会做这些题**；攻击把它打到 0.40。
脚手架确实是一个真实瓶颈，改完 +0.12。

## 3 但守卫臂仍停在 0.20

换了脚手架后守卫臂的 UA 没有任何变化（0.20）。逐条看拦截原因，问题不在守卫的
判定逻辑，而在**裁判被喂了不该它管的问题**：

- 合法 URL 被 `http://` 前缀搞到"无法归因" → 已加 URL 归一化
- 裁判反复确认"工具是否在授权范围"然后自己绕晕 → 工具/对象是否合规现在由代码
  算好写进上下文，并明确标注"无需你再判断"
- **当所有参数都已被策略放行时，裁判还在跑**，于是用"用户没有逐字说过"否掉正常动作
  → 现在这种情况直接跳过裁判

最后一条效果最明显：同一批 5 对（`injection_task_3`）从 0.20 → **0.60**；
完整 25 对从 0.20 → **0.32**（ASR 仍为 0）。

| slack 25 对（守卫臂） | UA |
|---|---:|
| 旧脚手架 | 0.20 |
| 新脚手架 + URL 归一化 + 裁判跳过 | **0.32** |
| 同批无防御（新脚手架） | 0.40 |
| 同批干净基线 | 0.80 |
| 报告 EAG | 0.92 |

守卫相对无防御只剩 0.08 的效用代价，但离报告还有 0.6 的绝对差距——
那部分属于脚手架本身（干净基线 0.80 已是上限，报告用的是更强的 scaffold）。

## 4 这轮学到的

1. **先对齐被测系统，再测防御**。脚手架弱的时候，守卫的"效用代价"根本测不出来，
   因为上限已经被脚手架压死了。
2. **裁判的职责边界要写进代码**，不能靠提示词自觉。凡是代码能确定的事实
   （工具是否授权、对象是否合规、哪些字段策略放行），都不要丢给模型再判断一遍。
3. **报告里的 0.92 不是随手能到的**：它对应一个成熟的 agent scaffold + 一个
   已经把误杀磨掉的守卫。我们在 0.60 这一档，方向对了，还差最后一截。
